# Native D3D9 shader compiler input

The native Intel user-mode driver needs a shader compiler in addition to its
current surface-copy path. Microsoft's independently installed runtime supplies
bytecode to `CreateVertexShaderFunc` and `CreatePixelShader`; those callbacks
receive explicit byte lengths. The native driver must validate/lower the program
and emit hardware code before it can publish a usable shader handle.

The implementation in `arch/x86/lib/intel_d3d9/shader.{c,h}` is the **token
decoder**, not that complete compiler. It has no runtime replacement, rendering
loop, shader interpreter, GPU submission or Microsoft code dependency. It is
not yet linked into `osito-intel9.dll`, and does not change `GetCaps` or the
currently unsupported shader callbacks.

## Decoder contract

- Accepts little-endian vertex/pixel SM2.0 and SM3.0, including unaligned input;
  other versions and unknown instruction layouts return `UNSUPPORTED`.
- Bounds the input to 16,384 DWORDs and the program to 4,096 instructions. These
  are decoder limits, not advertised Direct3D device capabilities.
- Requires exact instruction operand lengths and a terminal END; skips bounded
  comment payloads without interpreting embedded tokens. Rejects missing END,
  trailing bytes, reserved parameter/instruction bits and malformed operands.
- Produces a typed instruction stream with original DWORD offsets, opcode
  controls, swizzles, masks, modifiers, predicate operands, relative address
  registers/swizzles, declaration tokens and bit-exact constant definitions.
- A count-only first pass lets the caller size its instruction storage. A
  second pass publishes instructions only after successful syntax validation
  and capacity checks. Neither output buffer nor metadata changes on failure.
  Input/instruction overlap is rejected. The caller must provide an immutable
  input snapshot and disjoint output/metadata/error objects for both passes.
- Uses no heap, hidden mutable state, SDK headers or OS calls.

This reader deliberately does not establish register/capability limits,
stage/opcode legality, declaration consistency, definite writes, loop/call
structure or valid resource access. Even an empty or semantically invalid
program can be syntactically decoded. Successful decoding is **never** authority
to submit the input or generated commands to the GPU. Semantic validation,
lowering, register allocation, Intel EU emission, shader upload/lifetime and
the DDI callbacks remain to be implemented.

An observed token detail is covered by real compiler output: Microsoft's
`D3DAssemble` places a predication operand **after the destination and before
the ordinary sources**. Both `p0` and `!p0` fixtures preserve that ordering.
SM2 and SM3 `sincos` also use different source counts; the relative `a0`/`aL`
token must be included in each instruction's length.

## D3D9 to native Intel compiler, 2026-10-09

The next stage is implemented in `nir_frontend.{c,h}` and `compiler.mk`. It
feeds decoded D3D9 operations to NIR and the **native Intel compiler** from
Mesa 25.0.0. The separately installed Microsoft runtime remains the intended
Direct3D API implementation. This path uses no WineD3D, DXVK, Gallium Nine,
OpenGL/Vulkan runtime translation, CPU shader interpreter or software renderer.

The Intel compiler/support sources are a versioned subset under
`arch/x86/lib/intel_d3d9/mesa-intel/`. They match the existing Mesa/NIR version.
`source.json` records their hashes, the official release archive and its
SHA-256 (`96a53501fd59679654273258c6c6a1055a20e352ee1429f0b123516c7190e5b0`).
Additional include headers came from the same upstream GitLab tag. Local
portability changes retain their original upstream hash in `local_changes`.
The register-bank optimizer now uses Mesa's paired portable aligned allocation
and free functions in place of its POSIX-specific allocation pair. The local
metadata generator verifies every imported file and both VERSION files before
generation. Copyright notices and the upstream MIT license are retained.
These sources add no Microsoft binary or installer to the OS.

The frontend currently accepts PS2/PS3 straight-line programs with local DEF
constants, temporary registers, color output 0, swizzles, component write masks,
negation/absolute modifiers, saturation, MOV, ADD, SUB, MUL, MAD, MIN, MAX, ABS,
FRC, LRP, DP3 and DP4. It tracks which temporary components have been defined,
preserves components outside the write mask, and marks arithmetic exact to
avoid unintended contraction. Unsupported stages, instructions, declarations,
resource accesses and external constant bindings return an explicit failure.
Duplicate/late definitions, undefined temporary reads and incomplete output
also fail. This is an initial supported compiler subset, not full D3D9 shader
validation or a published device capability.

NIR output variables retain their semantic location for Intel's own I/O
lowering. The prototype initially used an already-lowered output with an
incorrect driver slot; the emitted program then lacked the color writes.
Keeping the output as a variable fixes that contract. The probe now checks
the expected four channels and requires a nonempty machine program with valid
dispatch metadata. Each SIMD entry is validated separately through its EOT;
alignment padding between entries is not an instruction stream.

`MINGW_ROOT` defaults to `C:/msys64/mingw64`; `OUT` remains overridable.
Windows uses native C11 synchronization/TLS implementations from Mesa and
the native toolchain runtime. The packed compiler IR uses GNU bitfield layout.
`win32_port.c` supplies the bounded memory search used by the instruction
validator; its 4,417 boundary cases pass with ASan/UBSan on Linux.

The PE linker checks unresolved references before removing all dead code.
The build therefore merges the compiler's LLVM IR first, internalizes its
implementation with only `main` public, and runs global dead-code elimination.

`win32_include/sys/` allow compilation of the Linux UAPI metadata types. No
`ioctl` implementation is supplied: Linux device queries must be unreachable
and removed, or linking fails. This is an offline compiler build, not a Linux
device service. A future compiler DLL must explicitly retain its own public
driver interface instead of this diagnostic `main`.

The final executable imports only `KERNEL32.dll`, `msvcrt.dll` and
`api-ms-win-core-synch-l1-2-0.dll`. No Mesa rendering runtime or external C++
runtime DLL is needed. All 34 positive cases and 20 rejections passed on

### Native CRT prerequisites (2026-10-09)

The updated kernel corrects `__getmainargs`/`__wgetmainargs`: process-owned,
writable user buffers, pointer cells/vectors of the importing PE's width,
ANSI/UTF-16 parsing, quoted program names, wildcard expansion of the final
path component, stable cached arrays and process-exit cleanup. Kernel metadata
is separate from the user arrays. The bounded parser follows the legacy
`msvcrt.dll` double-quote rule verified against the installed Windows DLL;
it must not be described as the newer UCRT quote grammar. Narrow parsing
currently assumes a single-byte or UTF-8 code page, not DBCS lead-byte rules.

`putc` now exports the existing character-output implementation. `fread`
continues short reads until the request, an error or actual EOF, counts only
complete elements, preserves pushed-back bytes and checks multiplication at
the caller's pointer width. Previously a 164-byte read into a 64 KiB buffer
returned without setting EOF, which made the compiler reject its input.

`WaitOnAddress`, `WakeByAddressSingle` and `WakeByAddressAll` share the native
NT wait records and scheduler cancellation/deadline machinery. Address queues
are hashed by process/address and use FIFO links; the timer never dereferences
the waiting process's memory. Registration and the later scheduler block are
reconciled under the same lock so a wake in between is retained. A normally
blocked task leaves the runnable queue; it does not poll with `Sleep`.

### Compiler embedded in the native UMD

`compiler_api.{c,h}` now owns a reusable Intel compiler context and returns a
versioned, 128-byte program header followed by owned bytecode and native code.
The header uses fixed-width integers and offsets rather than Mesa structures,
pointers or bitfields. It preserves SIMD entry offsets, dispatch GRFs, register
and scratch requirements, constants and the Gen9 dummy layer input. The latter
is necessary because the Intel compiler deliberately adds an input for its
header-only pixel shader workaround, even for constant-color programs.
Requirements outside this initial metadata contract are rejected explicitly.

Each call snapshots the bounded input before decoding, keeps compilation
scratch separate from the context, validates the emitted Intel instructions
and publishes the result only on success. Returned programs remain valid after
the input or compiler is destroyed. A context serializes compilation; distinct
contexts can coexist. This qualification checks sequential use of those
contexts, not concurrent compilation or destruction during an active call.
Exhaustive allocation-failure behavior inside the upstream compiler is also
not qualified.

The UMD lazily owns one context per device and implements pixel shader
creation, selection and deletion. Handles use the existing non-recycling
identity namespace and are checked against the device. Device destruction
releases outstanding shaders after successful runtime context destruction;
a failed callback preserves the live device and its shaders for retry.
There is still no draw callback or advertised render capability. Selecting
a shader does not change the fixed RCS program used by the copy diagnostic.

`compiler.mk` targets `umd api-test` build the compiler-backed driver and API
probe for `PLATFORM=win32` or `win64`; supply the local SDK/MSVC/WDK paths as
documented in the driver README. The packaging script additionally requires
the two compiled-driver directories. `generate-compiler-api-tests.py` embeds
the authored fixtures and independently qualified expected Intel programs;
it checks their existing SHA-256 receipts before generating the test header.

### Compiler-generated programs executing on Gen9

The native RCS builder now accepts owned compiler programs through an internal

### Device-owned shader storage

upload and unlock succeed. A successful lock's replacement allocation handle

CPU ownership or destroying the context.

### Queued native primitive work

### Ordered KMT synchronization on the native queue

The legacy `D3DKMTCreateSynchronizationObject[2]`, destroy, wait and signal
exports now connect to process-owned KMT objects and the native Intel job
queue. Mutexes, counting semaphores and legacy 64-bit fences are supported.
These are scheduler objects; they do not replace Microsoft's Direct3D runtime
or execute graphics on the CPU. Monitored/shared fences,
cross-device sharing, broadcasts, submission-time signals and fence rewind
remain unsupported. No CPU/GPU fence mapping or shared handle is invented.

Wait and signal calls admit operations into the context stream, following the
[KMT wait contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/ns-d3dkmthk-_d3dkmt_waitforsynchronizationobject2).
Only the oldest unfinished operation of each context may advance. An
unsatisfied wait leaves other contexts eligible to signal it. Signals at the
head of the stream follow retirement of earlier hardware work, consistent
with the default
[completion-time signal behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dukmdt/ns-d3dukmdt-_d3dddicb_signalflags).
An accepted call is not proof of GPU completion. The existing executor keeps
DMA resources until physical completion or acknowledged reset; logical close
and timeouts do not release them.

Synchronization handles share the typed, generation-protected KMT namespace.
Capture validates the process/device and retains every object atomically.
Destroy prevents new captures while queued operations keep their references.
Wait-all consumes nothing until all objects are ready. Cancellation competes
with the state update under the registry lock; a committed signal or semaphore
decrement cannot be undone. Closing the process, context or device cancels
uncommitted operations, and the deferred collector drops their references.
No provider callback, user copy, MMIO operation or hardware wait runs under
that registry lock.

### Native residency requirement accounting (public ABI pending)

requirement count separately from buffer pins, CPU views, and captured GPU

legacy pins and explicit cache synchronization are denied. The owner remains

## Context scheduling priorities

busy polling does not manufacture scheduling credit.

### Native device paging queues and deferred KMT retirement

### Immediate native residency requirements

### Blocking allocation access

### Native sampler program admission

`intel_gen9_resource_program_validate` and `intel_gen9_resource_shader_validate`
provide a separate ABI3 admission contract in `intel_gen9_shader.c`. They verify
the complete owned program, live texture/sampler masks, unique TEXCOORD-to-URB
mapping, optional dummy layer, constant-map bounds, exact Gen9 dispatch payload,
nonoverlapping ordered SIMD entries and canonical padding after EOT. Gen9's
header-only dispatch workaround requires a non-header phase (push constants or
an attribute); removing the dummy layer from a constant-coordinate program is
rejected. The existing capture/draw route remains ABI1/2 only.

Admission permits direct floating MOV/ADD/MUL, PLN interpolation from declared
coefficient/barycentric payloads, immediate-descriptor 2D sample SEND/SENDS and
single-target RT writes. Every texture instruction must use sampler N and
surface 1+N from the declared masks. Address registers, indirect descriptors,
predicates, other message operations, scratch and arbitrary memory access remain
rejected. Instruction compaction uses the existing Gen9 tables; validation is
structural and does not match a list of fixture hashes or execute shader code.

Per-GRF dataflow distinguishes logical eight-lane quarters from independently
initialized registers. This prevents scalar broadcasts and NoMask instructions
from consuming a sampler result whose lane zero or inactive lanes may be
undefined. Interpolation additionally tracks the provenance of both operands;
ordinary writes consume that provenance. SIMD32 uses two SIMD16 message groups;
both RT halves must be written exactly once before EOT. Cross-half payload use,
missing high-half RT selection and early EOT are rejected.

Both the legacy and resource validators enforce Gen9's high-GRF EOT payload
restriction and reject overlapping split-message payloads. The resource path
also checks the ordinary SEND response restriction involving r127 and source
overlap. These follow `send_restrictions` in the locally pinned Intel/Mesa
`brw_eu_validate.c`; all existing compiler fixtures remain accepted.

ASan/UBSan configuration, plus 12,000 malformed native-word trials per run.

## Native offered backing and transactional recovery

The native buffer manager can now release eligible offered backing while
retaining allocation identity, then allocate, certify, zero and synchronize
replacement pages before reopening access. This is groundwork for the runtime's
[video-memory offer/reclaim contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-memory-offer-and-reclaim).
The public KMT offer/reclaim exports are not connected yet.

Buffer discard refuses active pins, residency leases and CPU/GPU/coherent
access. Failed release retains the backing and its entire page charge. A failed
allocation leaves the discarded object retryable; invalid DMA provenance stays
quarantined. Cache preparation can retry existing replacement storage without
allocating another copy. Discarded or partially prepared backing cannot be
acquired for new work. New pages, including rounded padding, are cleared before
publication.

Manager offer validates the whole captured batch before closing admission.
Existing work retains its physical leases and can retire normally. Trim makes
a bounded pass through priorities 1 through 3, releases only eligible offered
storage and adjusts quotas only after successful release. Process quota
pressure restricts candidates to that PID, including its other devices and
incarnations. Allocator callbacks run outside the IRQ-safe manager lock.

Recovery uses stable caller-owned prepare/commit/release storage. Preparation
holds selected resource gates across allocation and cache callbacks; it charges
actual replacement pages, preserves partial recovery for retry and rechecks
device/process closure. Commit performs bounded metadata changes, permits
exactly one successful concurrent attempt and keeps per-item discarded results
available for future atomic PE output publication. Aborting before commit
preserves the offered/lost state. Property queries retain ordinary CPU cache
transition behavior but report busy while recovery is changing backing.

## Orderly process exit before releasing runtime resources

`ExitProcess` now coordinates DLL shutdown before the existing forced resource
teardown. The calling thread retains its TEB, static TLS and guest stack while
all other workers stop. When a worker requests exit, the primary's kernel
continuation parks at a safe point; its NT thread object becomes signaled but
remains retained for process cleanup. The worker executes the process-detach
callbacks itself, preserving its identity. The primary resumes only into
teardown after the exit request, never back into guest execution.

Thread creation is serialized with loader notifications and orderly exit. New
threads are rejected with error 5 during shutdown, matching the Windows probes.
Loader-lock waiters can observe cancellation; no owner is canceled while
publishing a new thread. The timer redirects only executable guest frames of
threads with pending cancellation, using their saved kernel continuations.
This stops CPU-bound guests without abandoning an interrupted kernel critical
section. The ordinary timer path uses atomic pending-work checks instead of
walking all Win32 contexts on every interrupt.

PE32 current-process pseudo-handle is normalized, and the previous call through

[ExitProcess documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-exitprocess).
