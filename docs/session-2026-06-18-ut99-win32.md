# Session 2026-06-18 - UT99 Win32 Playability

## Status

UT99 is validated playable under the x86 Win32 layer in QEMU/GTK. The user
verified that an in-game match now runs correctly, including mouse look and
player movement.

Scope: fix and validation are in the Osito-K Win32/NT compatibility layer, not
in the UT99 binaries. UT99 remains the reference workload because it is known to
work across NT versions on hardware and VMs.

## Symptoms Investigated

- Menu input worked, but earlier in-game camera/player movement did not.
- Starting a match later returned to the `osito>` shell.
- The framebuffer still showed UT pixels after the return to shell, indicating
  the PE process exited rather than QEMU or the kernel dying.

## Root Cause Of Shell Return

The serial log showed an Unreal critical error:

- `Ran out of virtual memory`
- `FMallocWindows::Malloc` / `FMallocWindows::Realloc`
- `NtAllocateVirtualMemory FAILED: STATUS_NO_MEMORY`
- `[K32] ExitProcess` followed by shell recovery

This was not VA address exhaustion: the monotonic Win32 VA allocator was still
far below `WIN32_VA_LIMIT`. The failure was physical page exhaustion caused by
`NtFreeVirtualMemory(MEM_RELEASE)` only writing tombstones into released ranges.
It did not unmap pages or return them to `mem_free_pages`, so long UT loading
paths leaked physical memory even though the app called `VirtualFree`.

The old `VM_TRACK_MAX` of 256 also let mappings fall out of the cleanup table,
which produced zero-sized releases and made the leak worse.

## Fix

File: `arch/x86/win32/ntsyscall.c`

- Raised `VM_TRACK_MAX` from 256 to 8192.
- Changed `NtFreeVirtualMemory(MEM_RELEASE)` to unmap each tracked page with
  `paging_unmap_page`.
- Returned the tracked backing allocation to the physical allocator via
  `mem_free_pages`.
- Kept VA recycling disabled in `win32_va_alloc` while stale engine pointer
  investigations remain open.

The important semantic change is that `MEM_RELEASE` now releases backing
physical pages. Stale VA use should fault instead of silently reusing old
backing or draining physical memory.

## Verification

Build:

```sh
make -C arch/x86 CLANG=1 SKIP_MODEL=1 EFI_PREFIX=/usr/local
```

Run:

```sh
arch/x86/scripts/ut99_debug.sh launch-gtk
```

Serial:

```sh
tail -160 /root/osito-run/serial.log
grep -n -E "\[K32\] ExitProcess|\[WINEXEC\] PE process exited|Critical Error|Ran out of virtual memory|osito>" /root/osito-run/serial.log
```

Expected post-fix evidence:

- `NtFreeVirtualMemory` logs `release size = ...`.
- No `Ran out of virtual memory`.
- No `Critical Error`.
- No `[K32] ExitProcess` from the UT process during normal play.
- QEMU remains alive and the game reaches interactive play.

Useful visual capture command:

```sh
arch/x86/scripts/ut99_debug.sh snap <name>
```

## Current Debug Baseline

Use `/root/osito-run/serial.log` as the primary source of truth. For UT99 Win32
regressions, keep the workflow simple: launch QEMU in GTK, let the user test the
gameplay path manually, then inspect serial markers and framebuffer captures.
