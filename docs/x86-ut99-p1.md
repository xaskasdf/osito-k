# UT99 on the physical ThinkPad P1

## Startup failure: installation layout (2026-09-25)

Launching `winexec Games/UT99/UnrealTournament.exe` loaded the PE32 executable
and Core, Engine and Window DLLs successfully, then returned to the shell.
The persisted `diag/boot3.log` identifies the immediate failure:

```text
[K32] CurrentDirectory='C:\Games\UT99'
[NT-CREATE-FAIL] path='Games\Textures\Palettes.utx'
[NT-CREATE-FAIL] path='Games\Help\Splash2.bmp'
[NT-CREATE-FAIL] path='Games\Help\Logo.bmp'
[MSGBOX-W] Critical Error: Assertion failed: Bitmap.LoadFile(Filename)
    [File:..\..\Engine\Inc\UnEngineWin.h] [Line: 55]
[WIN32] Execution finished, exit code = 1
```

The application's C++ exception handler catches the error and exits with code
1. This attempt does not establish a graphics, audio or CPU-fault failure.
The message-box shim logs the error, but the local terminal only shows the
prompt again. No Unreal process remained in the subsequent process list.

The installed files were partly flattened: executables, DLLs, localization,
packages and configuration were in `Games/UT99`, alongside loose help assets
and the Maps, Music, Sounds and Textures directories. The supplied
`Manifest.ini` specifies `System\UnrealTournament.exe` and `Help\Logo.bmp`.
The missing palette actually exists in `Games/UT99/Textures/Palettes.utx`.
Running one directory above System makes the engine's parent-relative paths
point outside the installation.

## Layout repair

The scoped repair creates copies under `Games/UT99/System` and
`Games/UT99/Help`, preserving all original files. It excludes logs, compressed
`.uz` payloads, subdirectories and the transient `Running.ini`. The existing
System log is preserved. The preflight inventory contains 383 files totaling
126,955,650 bytes.

In the System copies of Default.ini and UnrealTournament.ini, only the four
resource paths change; `Paths=*.u` remains local to System:

```ini
Paths=*.u
Paths=../Maps/*.unr
Paths=../Textures/*.utx
Paths=../Sounds/*.uax
Paths=../Music/*.umx
```

Renderer, audio, fullscreen and user settings are preserved.
The repair makes no kernel, bootloader, Win32 shim or game-binary patches.
The local shell launch command for the repaired layout is:

```text
winexec Games/UT99/System/UnrealTournament.exe
```

Launch remains a local-console operation: SSH intentionally disallows
`winexec`. Correct file placement alone does not prove menu rendering,
gameplay, input or audio work on this machine.

`dmesg` did not contain the latest launch: before the 2 MiB kernel log wraps,
`klog_read` returns the beginning when the caller's buffer is smaller than
the accumulated log. The shell's 512 KiB buffer therefore missed the recent
error. Downloading the persisted 1,156,809-byte boot log via file sync avoided
this truncation; the logging implementation is not fixed by this repair.

The 2026-09-26 diagnostic follow-up fixes the newest-suffix selection in
`klog_read`; the layout repair itself did not. `dmesg` remains bounded to
512 KiB, so an older failure can still age out of that view.

The first copy attempt also exposed a separate shell `cp` defect:
`kmalloc(0)` for an empty INI is reported as out of memory. The repair uses
`touch` for empty files and verifies existing copies before resuming. That
message was not evidence of physical RAM exhaustion. The shell implementation
itself is unchanged.

## Recovery dialog controls (2026-09-26)

Remote capture of the physical P1 succeeded with the game open. The recovery
dialog showed its logo and explanatory text, but a blank lower panel covered
all four recovery buttons. The same failure reproduced with the unmodified
game's `-safe` argument in QEMU, without NVIDIA hardware. Window.dll resource
2020 creates a group box followed by four sibling buttons; child insertion
correctly leaves the older group box above them in the retained z-order.
Painting that group box as an opaque rectangle hid the buttons, and the native
control also intercepted pointer targeting.

The generic BUTTON implementation now paints only the group border and label,
requests `WM_CTLCOLORSTATIC`, and returns `HTTRANSPARENT`. Its retained surface
uses explicitly enabled pixel coverage; ordinary windows retain the opaque
compositor path. Repainting clears coverage only through the DC's current clip.
Pointer targeting skips an unsubclassed native group box. Application-defined
hit-test overrides and arbitrary cross-thread `HTTRANSPARENT` routing are not
claimed as implemented by this correction.

The PE32 and PE64 control probes both pass 70 checks on Windows and Osito-K.
They cover the non-erasing interior, color callback, hit-test result, dialog
code and explicit `BM_CLICK` notification. The Windows comparison caught a
separate prior mismatch: an explicit `BM_CLICK` does notify the group-box owner
even though physical pointer hit testing is transparent.

In `arch/x86/build/ut-recovery-qemu-20260926-r4/`, screenshots show all four
buttons, and an actual USB-tablet click on the safe-mode button opens its
checkbox page. There are no page faults in that run. The identical tested
7,156,960-byte image, SHA-256
`caa9462df961707d7ef0bfca11c27c757fef4afcd479a921ca34979acf1d2c18`,
was uploaded to the P1 as `/kernel-groupbox-20260926.elf`; kexec returned to SSH
automatically with the pinned identity. This did not update the EFI boot image
or establish physical gameplay validation.

At this stage, native Win32 frames were a separate missing contract. Resource 104 requests
caption and system menu (`0x80c80ac0`), but not minimize/maximize buttons. The
layer conflated client and outer geometry: `AdjustWindowRect` was a stub,
default `WM_NCHITTEST` returned the client area, and nonclient painting was absent.
The follow-up needed coherent `WM_NCCALCSIZE`, client/window DCs, child coordinate
mapping, caption hit testing and style-dependent system commands. Adding a
decorative border to every surface would break custom-chrome/fullscreen clients
and would not satisfy that contract. Keyboard tab traversal is also not proven
by the successful pointer test. No game-specific rendering bypass is added.

## Pixel formats, frames and PS/2 input (2026-09-26)

The software renderer's incorrect colors reproduced without NVIDIA hardware.
SoftDrv uses a 16-bit RGB555 DIB with explicit `7C00/03E0/001F` masks. The GDI
layer discarded these masks and interpreted the buffer as RGB565. Bitmap/DC
state now retains masks and palettes, validates DIB formats and consistently
converts pixels in the relevant DIB, blit and readback paths. `BI_RGB` at 16 bits
uses RGB555. `GetObject` exposes the PE32/PE64 `DIBSECTION` layouts. `StretchBlt`
performs bounded nearest-neighbor conversion instead of returning success
without copying. The old UT-specific BitBlt fullscreen presentation path is
removed; the compositor owns presentation.

The frame implementation now distinguishes outer and client rectangles through
`WM_NCCALCSIZE`, `AdjustWindowRect[Ex]`, child positioning, coordinate mapping,
client/window DCs and size notifications. Standard captions paint the controls
requested by their styles and dispatch close, minimize, maximize/restore and
caption dragging. Dialog resource dimensions remain client dimensions, so their
lower controls are no longer clipped by the caption. A custom NCCALCSIZE
handler can retain a borderless client; exclusive DirectDraw does not acquire a
decorative frame. Recovery requests a caption and close button, not min/max.

Real QMP keyboard injection exposed another independent cause of missing input:
PS/2 decoded events reached the shell/desktop but never entered the Win32 input
queue. The PS/2 path now forwards decoded scans through
`win32_post_keyboard_scan`; it does not share an E0-prefix accumulator with USB.
Pause has an explicit press/release pair. Protocol bytes, fake shift prefixes,
console-injected text and DOS-captured input are not forwarded. Interrupt-side
code enqueues events rather than invoking application callbacks.

## DirectDraw display modes (2026-09-26)

Adapter enumeration now exports `DirectDrawEnumerateW` and
`DirectDrawEnumerateExA/W` as well as the ANSI entry point. Callbacks receive
application-addressable strings with the correct PE32/PE64 calling convention,
not truncated pointers to kernel strings. The software display is the primary
adapter (NULL GUID/monitor); this does not advertise a hardware NVIDIA driver.

`EnumDisplayModes` validates the 108/124-byte descriptor contracts, honors
width/height/depth/refresh filters, writes refresh at the correct offset and
stops after callback cancellation. Refresh enumeration remains the existing
logical 60-Hz software-display model. This is not IDirect3D7 implementation:
the real D3DDrv still requires that missing interface. The separate
`UTVideoP1.ini` selects SoftDrv without replacing `UnrealTournament.ini`.
Launching with `Entry.unr INI=UTVideoP1.ini` avoids parsing INI as a network URL.

Validation in `arch/x86/build/ddraw-display-fixed-20260926/`: PE32 434 checks,
PE64 126 checks, zero failures; physical P1 PE32 224 checks, zero failures.
Native Windows PE64 passed 1472 checks. Native PE32 ran 7519 checks with three
failures because native DirectDraw continued enumeration after callback
cancellation; these discrepancies remain recorded rather than hiding them.
PE64 checks cover adapter/USER32 contracts, not DirectDraw COM mode callbacks.

UT's windowed SoftDrv menu has a built-in list ending at 800x600. Its fullscreen
path queries DirectDraw. In `ut-video-modes-20260926-r3/`, the real engine
accepted `togglefullscreen`, then `setres 1280x800x32`, and rendered the menu and
practice dialog at the requested size. Alt+Enter is not validated. That run
ended on the test driver's manual-UI timeout, not a game exception. The P1
user confirmed fullscreen; its log records 1920x1080 primary/back buffers,
initially 16-bit and then 32-bit. The following crash occurred when selecting
Capture the Flag, not simply when entering fullscreen.

## CTF exception dispatch (2026-09-26)

`ddraw-display-20260926/p1-fullscreen-crash.log` captures a typed MSVC C++
exception (`E06D7363`) beginning in Core's `GetPackageLinker`. There is no
initial CPU page/general-protection fault. The game's generic "General
protection fault" dialog is not evidence of a CPU #GP. Its on-disk log was
empty, so the kernel trace and controlled reproduction are authoritative.

Three layer defects were isolated:

- A value catch received the address of the exception object, rather than its
  contents. For a thrown string pointer this supplied a pointer-to-pointer.
  Catch initialization now distinguishes values/references, copies the full
  object size with range checks and applies metadata pointer adjustments.
- A later C++ exception reused a saved registration cursor from a completed
  catch. Dispatch now follows the live FS exception chain, which may contain
  newly installed handlers.
- Nonlocal-transfer cleanup treated any destination on the main stack as an
  exit from all callbacks. WndProc callbacks also use that stack. Each callback
  now records its actual return slot; cleanup preserves callbacks containing
  the destination and abandons only the exited ones.

The first two corrections alone reproduced a fatal callback-depth underflow
when selecting CTF in a window in `ut-cxx-catch-20260926-r1/`. Thus the failure
does not require fullscreen or physical graphics hardware. The subsequent
`ut-cxx-catch-20260926-r2/` kernel passes the expanded C++ probe: 69 checks,
zero failures, matching native Windows. Coverage includes scalar and pointer
values, references, trivial objects, catch-slot bounds, sequential exceptions,
nested WndProc catches and exceptions escaping one to three callbacks. Existing
unwind32, SEH3 and SEH4 probes also exit successfully.

The real-game run then selected Capture the Flag without exiting, displayed
the CTF-Beatitude preview, loaded the level, switched to fullscreen and entered
play after a QMP mouse click. `ctf-selected.png`, `ctf-started.png`,
`ctf-fullscreen.png` and `ctf-play.png` record those stages. The engine's `quit`
command returned exit code zero, `console: idle` and
`vm(entries/private/mapped_pages)=0/0/0`. This run used `-nosound`; it does not
validate audio or long-duration gameplay.

The frozen 7,119,992-byte r2 kernel has SHA-256
`60a9d81f8b704ba24586d53f02c265a08d18ad7c0d78e6630ccdb9b5a93ccff4`.
It was transferred as `/kernel-cxx-catch-20260926.elf` and hotloaded on the P1.
Wi-Fi/SSH returned automatically and the physical C++ probe also passed 69/69
checks (`p1-cxx-probe.log`). Desktop and UT were relaunched remotely using the
existing separate profile. At deployment, physical repetition of the CTF menu
selection was still pending; the USB EFI kernel was not replaced by this
hotreload.

In the subsequent `p1-retest-dmesg.log`, the user's physical interaction enters
1920x1080x32 fullscreen and traverses the same six Core typed catches seen in
the failing selection. It continues processing input and later exits with
`ExitProcess(0)` and zero tracked Win32 pages, without the callback underflow.
The concurrent screenshot request ended with an SSH channel reset; there is
no valid P1 image from this attempt. This supports recovery through the
previous failure path. The game is no longer running at the end of this log.

The user subsequently confirmed that selecting Capture the Flag displays the
preview and starts the match correctly on the physical P1, and accepted this
UT graphics/debugging work as complete. A separate direct CTF-Beatitude launch
also remained responsive. Remote capture is a separate open transport issue:
the desktop screenshot transferred and verified in 6.3 seconds, while both
compressed and raw captures during gameplay timed out. This does not invalidate
the user's visual result, nor establish that the screenshot transport is fixed.

This is not complete MSVC C++ exception support. Nontrivial catch copy
constructors are explicitly unsupported instead of supplying a bogus object.
Destructor ownership, full nested rethrow lifetime and thread-local exception
records remain separate work. These changes do not suppress game exceptions
or special-case CTF/package names.
